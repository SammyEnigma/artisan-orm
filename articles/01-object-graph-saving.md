In this article you will learn how to save an object graph in a master-detail relationship with one stored procedure.

## Introduction

I have a web client that sends data to my ASP.NET application in JSON format. The data is an object graph in master-detail relationship — or even a collection of object graphs. The data is deserialised into C# object graphs by a Web API controller. I want to save that C# object graph with ADO.NET and **one stored procedure**. And I want to do this without GUIDs, XML or EF.

## Background

Let's suppose that a web client sends object graphs consisting of three objects:

- `GrandRecord`
- `Record`
- `ChildRecord`

A collection of `GrandRecord`s where:

- each `GrandRecord` has a collection of `Record`s,
- each `Record` has a collection of `ChildRecord`s,
- `Id` is an integer auto-generated by the database,
- and while an object is not yet saved, its `Id` has the value `0`.

Here is a sample of the object-graph collection:

```text
                      Id, Name
GrandRecord           1,  (A)
    Record            |-- 2, (A)A
        ChildRecord       |-- 3, (A)Aa
        ChildRecord       |-- 0, (A)Ab
    Record            |-- 0, (A)B
        ChildRecord       |-- 0, (A)Ba
        ChildRecord       |-- 0, (A)Bb
GrandRecord           0,  (B)
    Record            |-- 0, (B)A
```

Or the same in JSON format:

```json
{
  "grandRecords": [
    {
      "id": 1,
      "name": "(A)",
      "records": [
        {
          "id": 2,
          "name": "(A)A",
          "childRecords": [
            { "id": 3, "name": "(A)Aa" },
            { "id": 0, "name": "(A)Ab" }
          ]
        },
        {
          "id": 0,
          "name": "(A)B",
          "childRecords": [
            { "id": 0, "name": "(A)Ba" },
            { "id": 0, "name": "(A)Bb" }
          ]
        }
      ]
    },
    {
      "id": 0,
      "name": "(B)",
      "records": [
        {
          "id": 0,
          "name": "(B)A",
          "childRecords": []
        }
      ]
    }
  ]
}
```

On the web server, the above JSON is deserialised into object graphs of three classes:

```csharp
public class GrandRecord
{
    public int            Id       { get; set; }
    public string         Name     { get; set; } = null!;
    public IList<Record>  Records  { get; set; } = new List<Record>();
}

public class Record
{
    public int                  Id             { get; set; }
    public int                  GrandRecordId  { get; set; }
    public string               Name           { get; set; } = null!;
    public IList<ChildRecord>   ChildRecords   { get; set; } = new List<ChildRecord>();
}

public class ChildRecord
{
    public int     Id        { get; set; }
    public int     RecordId  { get; set; }
    public string  Name      { get; set; } = null!;
}
```

Now the object graphs have to be saved with one stored procedure into three database tables:

```sql
create table dbo.GrandRecords
(
    Id    int          not null  identity  primary key clustered,
    Name  varchar(30)  not null
);

create table dbo.Records
(
    Id             int          not null  identity  primary key clustered,
    GrandRecordId  int          not null,
    Name           varchar(30)  not null,

    foreign key (GrandRecordId) references dbo.GrandRecords (Id) on delete cascade
);

create table dbo.ChildRecords
(
    Id        int          not null  identity  primary key clustered,
    RecordId  int          not null,
    Name      varchar(30)  not null,

    foreign key (RecordId) references dbo.Records (Id) on delete cascade
);
```

The question is: how?

## Solution

Of course, table-valued parameters for the stored procedure are part of the answer.

Given these user-defined table types:

```sql
create type dbo.GrandRecordTableType as table
(
    Id    int          not null  primary key clustered,
    Name  varchar(30)  not null
);

create type dbo.RecordTableType as table
(
    Id             int          not null  primary key clustered,
    GrandRecordId  int          not null,
    Name           varchar(30)  not null
);

create type dbo.ChildRecordTableType as table
(
    Id        int          not null  primary key clustered,
    RecordId  int          not null,
    Name      varchar(30)  not null
);
```

The stored procedure for saving the above object graphs starts with:

```sql
create procedure dbo.SaveGrandRecords
    @GrandRecords  dbo.GrandRecordTableType  readonly,
    @Records       dbo.RecordTableType       readonly,
    @ChildRecords  dbo.ChildRecordTableType  readonly
as
```

So we have to collect all data by type (`GrandRecord`, `Record` and `ChildRecord`), create ADO.NET `DataTable`s and pass them to the stored procedure.

But — because our tables are linked by foreign keys `GrandRecordId` and `RecordId`, we have to somehow preserve that link while converting the object graph into the separate `DataTable`s. What is more, the identities of new objects have to be **unique** — otherwise, we cannot distinguish the `Record`s of `GrandRecord (A)` from the `Record`s of `GrandRecord (B)`.

However, as we remember, new objects have `Id = 0`.

To fix this, let's assign **ever-increasing negative identities** to object Ids that are equal to `0`:

```csharp
var id = int.MinValue;

foreach (var grandRecord in grandRecords)
{
    if (grandRecord.Id == 0)
        grandRecord.Id = id++;

    foreach (var record in grandRecord.Records)
    {
        if (record.Id == 0)
            record.Id = id++;

        record.GrandRecordId = grandRecord.Id;

        foreach (var childRecord in record.ChildRecords)
        {
            if (childRecord.Id == 0)
                childRecord.Id = id++;

            childRecord.RecordId = record.Id;
        }
    }
}
```

Now it is time to populate the `DataTable`s. For example, here is how to prepare a `DataTable` with `Record` data:

```csharp
var recordTable = new DataTable("RecordTableType");
recordTable.Columns.Add("Id"           , typeof(int));
recordTable.Columns.Add("GrandRecordId", typeof(int));
recordTable.Columns.Add("Name"         , typeof(string));

var records = grandRecords.SelectMany(gr => gr.Records);

foreach (var record in records)
{
    recordTable.Rows.Add(new object[]
    {
        record.Id,
        record.GrandRecordId,
        record.Name
    });
}
```

After the `DataTable`s are prepared, the stored procedure receives the following data in its table-valued parameters:

`@GrandRecords`

| Id          | Name |
|------------:|------|
| 1           | (A)  |
| -2147483648 | (B)  |

`@Records`

| Id          | GrandRecordId | Name  |
|------------:|--------------:|-------|
| 2           | 1             | (A)A  |
| -2147483647 | 1             | (A)B  |
| -2147483646 | -2147483648   | (B)A  |

`@ChildRecords`

| Id          | RecordId    | Name   |
|------------:|------------:|--------|
| 3           | 2           | (A)Aa  |
| -2147483645 | 2           | (A)Ab  |
| -2147483644 | -2147483647 | (A)Ba  |
| -2147483643 | -2147483647 | (A)Bb  |

## Object Graph Saving Technique

To insert new, update existing and delete old data in one go, SQL Server provides the `MERGE` statement. The `MERGE` statement has an `OUTPUT` clause that can collect both the just-inserted Ids and the Ids from the source (parameter) table.

So the technique to save all three tables with correct foreign keys is:

1. Save `@GrandRecords` and collect `(InsertedId, ParamId)` pairs from its `OUTPUT`.
2. When saving `@Records`, translate each `GrandRecordId` from its negative-identity value to the real inserted value, using the pairs from step 1. Collect `(InsertedId, ParamId)` pairs from this step too.
3. Repeat for `@ChildRecords`, translating `RecordId` via the pairs from step 2.

Behaviour summary for each branch of `MERGE`:

- **`when matched`** (record exists in both `target` and `source`): `MERGE` does an `UPDATE`. `inserted.Id` and `source.Id` are equal to the existing Id.
- **`when not matched by target`** (record exists in `source` only): `MERGE` does an `INSERT`. `inserted.Id` is the **new** identity assigned by the database, `source.Id` is the **negative** placeholder.
- **`when not matched by source`** (record exists in `target` only): `MERGE` does a `DELETE`. `inserted.Id` and `source.Id` are `NULL`, but `deleted.Id` carries the Id of the deleted record.

Here is the stored procedure that saves our object graph:

```sql
create procedure dbo.SaveGrandRecords
    @GrandRecords  dbo.GrandRecordTableType  readonly,
    @Records       dbo.RecordTableType       readonly,
    @ChildRecords  dbo.ChildRecordTableType  readonly
as
begin
    set nocount on;

    declare @GrandRecordIds table (              -- translation table
        InsertedId  int  primary key,
        ParamId     int  unique
    );

    declare @RecordIds table (                   -- translation table
        InsertedId  int           primary key,
        ParamId     int           unique,
        [Action]    nvarchar(10)
    );

    -- save GrandRecords
    merge into dbo.GrandRecords as target
        using
        (
            select Id, Name from @GrandRecords
        )
        as source on source.Id = target.Id

    when matched then
        update set
            Name = source.Name

    when not matched by target then
        insert (Name)
        values (source.Name)

    output                                       -- collect translation Ids
        inserted.Id,
        source.Id
    into @GrandRecordIds (InsertedId, ParamId);


    -- save Records
    merge into dbo.Records as target
    using
    (
        select
            Id            ,
            GrandRecordId =  ids.InsertedId,    -- Id translation target
            Name
        from
            @Records r
            inner join @GrandRecordIds ids
                on ids.ParamId = r.GrandRecordId  -- Id translation source
    )
    as source on source.Id = target.Id

    when matched then
        update set
            GrandRecordId = source.GrandRecordId,
            Name          = source.Name

    when not matched by target then
        insert (GrandRecordId, Name)
        values (source.GrandRecordId, source.Name)

    when not matched by source
        and target.GrandRecordId in (select InsertedId from @GrandRecordIds) then
            delete

    output                                       -- collect translation Ids
        isnull(inserted.Id, deleted.Id),
        isnull(source.Id,   deleted.Id),
        $action
    into @RecordIds (InsertedId, ParamId, [Action]);

    delete from @RecordIds where [Action] = 'DELETE';


    -- save ChildRecords
    merge into dbo.ChildRecords as target
        using
        (
            select
                Id        ,
                RecordId  =  ids.InsertedId,     -- Id translation target
                Name
            from
                @ChildRecords cr
                inner join @RecordIds ids
                    on ids.ParamId = cr.RecordId  -- Id translation source
        )
        as source on source.Id = target.Id

    when matched then
        update set
            RecordId = source.RecordId,
            Name     = source.Name

    when not matched by target then
        insert (RecordId, Name)
        values (source.RecordId, source.Name)

    when not matched by source
        and target.RecordId in (select InsertedId from @RecordIds) then
            delete;
end;
```

## Important Notice

> In the `MERGE` statement, the source and the target tables **must** have clustered indexes on their join columns. This prevents deadlocks and guarantees insertion order.

The join columns are in the `as source on source.Id = target.Id` line of each `MERGE` statement.

That is why the user-defined table types above have `primary key clustered` in their definitions.

That is why the negative identities are ever-increasing and start with `int.MinValue`.

Note also the `on delete cascade` clause on the foreign keys in the permanent tables. It allows child records to be deleted when their parent records are deleted by the `when not matched by source ... then delete` branch of `MERGE`.

## Where This Lives in Artisan.Orm

The patterns above became the foundation of Artisan.Orm:

- The `dbo.GrandRecords` / `dbo.Records` / `dbo.ChildRecords` tables, the matching `dbo.*TableType` user-defined table types, and the `dbo.SaveGrandRecords` stored procedure live in the [`Database/`](../Database/) project.
- The C# repository, mappers (with `Int32NegativeIdentity` for negative-id assignment) and integration tests live in [`Tests/DAL/GrandRecords/`](../Tests/DAL/GrandRecords/).
- The library's `Int32NegativeIdentity` / `Int64NegativeIdentity` / `Int16NegativeIdentity` static classes encapsulate the "next ever-increasing negative number" generator so each mapper just calls `obj.Id = Int32NegativeIdentity.Next` instead of threading a counter through the loop.

The wiki page [Negative identities and object graph saving](https://github.com/lobodava/artisan-orm/wiki/Negative-identities-and-object-graph-saving) covers the same ground from the library-API perspective; this article is the long-form story behind it.
